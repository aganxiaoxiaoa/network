## 3. 待验证假设分析

遵循科学严谨的调查原则，在未获取 AP 侧运行日志、未进行空中无线报文抓包及驱动崩溃调试前，严禁妄断。客观列出以下待验证假设：

### 假设 A：无线网络环境变化或射频链路波动
- **事实支持**：WLAN 事件日志中出现的“网络被驱动程序断开连接”（Event 8003）只是 Windows 系统的通用断开分类字段，不等于确认驱动/固件本身有缺陷；随后两次重连报 RSSI 255（无有效射频测量），表明当时天线端未能与 AP 建立有效射频交互。
- **存疑点**：单机日志无法证明是否由环境遮挡、信道干扰或硬件瞬态引发。

### 假设 B：测试期间的脚本调用影响
- **事实支持**：断网发生时间点与前期工具开发验证的脚本执行存在时间交叠。
- **存疑点**：终端历史中没有捕获到直接导致网卡硬件挂起的具体指令执行栈，无法孤立确认相关性。

### 假设 C：本地看门狗行为
- **事实排除**：看门狗日志显示在 01:28:13 仅执行了 `ipconfig /flushdns`；由于安全参数 `-AllowNicReset:$false`，看门狗记录 `Not touching the adapter`，**已 100% 排除本地看门狗主动禁用或重启网卡的嫌疑**。

### 假设 D：无线路由器 (AP) 侧信道跳变 (DFS) 或踢线
- **事实支持**：Wi-Fi 6E (802.11ax) 在 5GHz/6GHz 频段下遭遇雷达信号会执行 DFS 避让跳变，导致客户端瞬间掉线并在数十秒内无法发现原网络。
- **存疑点**：单机环境未接入路由器后台，缺乏 AP 侧日志交叉比对。

## 6. 本轮调查新证据与假设修正 (2026-09-10 补充)

随着本轮诊断工具箱在网卡高级属性语义分类与现代待机会话关联分析能力的完善，调查团队获取到如下关键客观新证据，并对既有假设做出科学修正：

### 6.1 激进省电开关假设经实测排除 (不成立)
- **客观实测证据**：
  通过 `Get-AdapterAdvancedPowerProperties` 语义化分类对本机 MediaTek Wi-Fi 6E MT7922 网卡的高级属性进行全量只读枚举：
  - `LowPowerEnable` (省电)：当前值为 `已禁用` (`0`)；
  - `UAPSDSupport` (U-APSD Support)：当前值为 `已禁用` (`0`)；
  - 需关注类激进省电项开启数实测为 **`0` 项**。
- **调查结论**：
  网卡驱动底层并未开启任何激进的主动节能或低功耗微睡眠特性，**此前关于“网卡被开启了激进省电开关导致微睡眠断网”的假设不成立，予以排除**。

### 6.2 现代待机架构与事故时段 Kernel-Power 事件核验
- **客观实测证据**：
  1. 系统电源架构核验（`powercfg /a`）确认系统支持并运行在 `待机 (S0 低电量待机) 连接的网络` 架构下，网卡不暴露传统电源管理复选框。
  2. 针对事故发生时段（2026-09-10 01:20 至 01:35）检索系统日志中的 `Microsoft-Windows-Kernel-Power` 事件：经核验，事故发生时段无任何 Kernel-Power 事件记录，最近的一条内核电源事件发生在 `2026-09-09 22:52:08`。因此在该时段，Kernel-Power 事件已不可用，无法直接验证断网时是否存在低功耗会话转换。
  3. **统计口径重大纠正**：此前曾误将 Event 11004（17 次）与 Event 8003（8 次）简单相加报告为“25 次断开”。经本轮属性深度枚举核实，Event 11004 的 `SecurityHintCode = 0`，提示文本为“操作成功。”，属于正常的安全会话拆除流程，非故障事件。**真实断开次数严格为 7 天 8 次（仅限 Event 8003）**。
  4. 全量 168 小时（7 天）回溯分析显示：在全部 8 次真实的 WLAN 8003 断开事件中，8 次均发生在系统完全清醒活跃期，0 次发生在待机会话内，0 次发生在唤醒后 30 秒内。

### 6.3 新增待验证假设 E：GTK Rekey 硬件卸载与 WPA 密钥协商时序竞争
- **客观证据支撑**：
  1. 网卡高级属性中，`GTK Rekey for WOWLAN`（注册表键 `DisableGTKRekey`）当前处于 `已启用` 状态（属于 4 项正常网络卸载类属性之一）。
  2. 事故时间线显示：断网前 5 秒（01:26:51）系统先收到 `Event 11004 (无线安全已停止)`，随后（01:26:56）触发 `Event 8003 (网络被驱动程序断开连接)`，而在重连阶段（01:28:54）明确记录了 `Event 11006 (动态密钥交换未能在配置的时间范围内成功)`。
- **待验证机理**：
  GTK (Group Temporal Key，组临时密钥) 由无线路由器（AP）周期性广播更新。开启 `GTK Rekey for WOWLAN` 意味着由网卡固件协助代理处理组播密钥更新。当路由器发起周期性 GTK 更新，若网卡固件未能按时回复或在多核并发下处理超时，路由器端按 802.11 协议标准会主动向客户端发送 Deauth（解关联断开），从而触发客户端记录驱动断开与安全握手超时。
- **存疑与待验证点**：
  需要捕获路由器端 syslog 或在故障复现时进行无线空口抓包，以确认是否有路由器发出的 EAPOL/GTK 请求未得到应答。

### 6.4 WLAN 8003 原因码取证与网卡驱动基线记录
- **Event 8003 原因码事实**：
  实机取样与 `WlanReasonCodeToString` 官方 API 调用证实，本机 7 天内全部 8 次 Event 8003 的 `ReasonCode` 结构化属性均恒为 `0`（`0x00000000`），官方 API 翻译为 `The operation was successful.`，本地化事件文本为“网络被驱动程序断开连接。”。这意味着在操作系统及 NDIS 层面，网卡驱动并未向系统上报任何具体的 802.11 协议层断开错误代码，系统日志中无底层协议原因可查。
- **活动网卡驱动基线记录 (只记录不评价，作为后续比对基线)**：
  - 适配器描述: MediaTek Wi-Fi 6E MT7922 160MHz Wireless LAN Card
  - 驱动版本 (DriverVersion): `3.4.2.1123`
  - 驱动日期 (DriverDate): `2024-11-15`
  - 驱动提供商 (DriverProviderName): `MediaTek, Inc.`
  - INF 文件名称 (InfName): `oem67.inf`

### 6.5 新增待验证假设 F：驱动/固件层链路维持不稳
- **客观证据支撑**：
  1. 全部 8 次 Event 8003 的前置 60 秒内事件均严格为 Event 11004，且 8003 结构化属性中的 ReasonCode 恒为 0，文本均指向驱动程序主动向系统发起断开。
  2. 8003 断开事件的时间间隔分布极不均衡（最小 197 秒，最大 45263 秒，平均 14428.6 秒），不存在固定的定时周期。

### 八、取证方法学：已判定不可信的信号（重要，避免后续误判）
1. 看门狗的 wanOk（TCP 连接 223.5.5.5:53 等公网端口）: WinDivert 处于 Running，原生 socket 无法排除包层劫持，不可作为链路证据
2. 看门狗的 adapterUp: Test-AdapterUp 仅检查 NDIS 的 Status -eq 'Up'，不查询 802.11 关联状态，不能证明当时仍处于关联
3. 单次 ICMP ping: 看门狗 Test-GatewayAlive 只发 1 个 ping，脚本自身注释即指出繁忙路由器丢一个 ping 不代表链路故障
4. NetworkProfile 的 10001 与 NCSI 的 CapabilityReset: 全部出现在 8003 之后 0.005 ~ 0.5 秒，属被动镜像，无预警价值

### 九、待验证的主假设
问题起点位于 802.11 安全/密钥层，而非射频层或 IP 层。
表现为安全会话先被拆除（11004，安全提示为「操作成功。」），随后 4.2 ~ 8.7 秒链路才被驱动判定断开（8003，ReasonCode 0）。
需要在下一次断开发生时以秒级分辨率取证才能定案或推翻。

### 十、下一次断开的取证操作手册
1. 在切回 SSID 701 之前先启动采样器:
   powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\app\NetworkDiagnostics.ps1 -Action Watch -IntervalSeconds 1 -PingCount 1 -DurationMinutes 0
2. 实测性能: 稳态采样节奏 1.230 秒（PingCount=1）/ 1.216 秒（PingCount=0），单轮耗时 215.5 ms / 203.8 ms。
   注意首轮 CycleMs 为 3776 ms、首个采样间隔为 4.790 秒（模块加载开销），启动后前约 5 秒的数据不可用，必须提前启动。
3. 断开发生后，取 CSV 中 8003 时间点之前的若干行，按以下标准判读:
   - 若出现 AdapterStatus=Up 且 RxDelta=0 且 GatewayArpState 不为 Reachable 的连续若干轮，则证实「关联保持、数据面停摆」
   - 若 RxDelta 一直正常直到 AdapterStatus 变为 Disconnected 的同一轮，则推翻该假设，说明是瞬时掉链
4. 判读时不得使用 wanOk 类经代理路径的数据作为证据。
